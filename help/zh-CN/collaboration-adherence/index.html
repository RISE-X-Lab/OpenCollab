结果与记录

检查团队是否真的按分工协作

Team 的分工写在 team.yaml 里，但声明的分工不保证会被执行：入口成员可能把活派给 Coder 之后又自己写完了全部代码，最后也不采纳 Coder 的改动。Adherence（依从性）指的就是：对比团队声明和运行记录，检查实际协作是否符合声明。

OC 提供两样东西：离线读取团队声明的 opencollab.teams 接口，以及带成员身份的轨迹事件。批量统计和报告在评测项目 OCE 那边。

第一步：读出团队声明

opencollab.teams 不用真的启动运行，就能读出团队声明。下面读取仓库自带的团队文件，你也可以换成自己的 YAML。读取时会解析配置和关联的提示词文件，适合在发起运行之前把实验条件存下来。

from opencollab.teams import (
    declared_context_policy,
    declared_role_budgets,
    declared_role_names,
    declared_role_profiles,
    declared_role_tools,
)

team_file = "configs/team.collab.yaml"
print(declared_role_names(team_file))     # 角色名册，入口角色排第一
print(declared_role_tools(team_file))     # 各角色声明的工具
print(declared_role_budgets(team_file))   # 各角色预算
print(declared_role_profiles(team_file))  # 各角色配置
print(declared_context_policy(team_file)) # 上下文策略

怎样理解返回结果：

  • 角色名已经归一化，入口角色排在名册第一位。
  • 工具名按文件里的声明顺序返回。实际启动时还会做能力筛选、补上后备工具组合，所以运行时的工具不一定和这里完全一样。
  • 预算结果是空字典，说明团队使用调用方提供的共享额度；YAML 里写了每个角色的额度时，要求固定名册。
  • 上下文结果包含 policy 与 tool_result_budget。
  • 想按提示词内容分组，用同模块的 declared_role_prompt_digests，它读取包含 prompt_file 内容的提示词摘要。

也可以在命令行查看入口角色、声明工具和通信边：

opencollab team show --team-config configs/team.collab.yaml

分析时保留完整的声明名册，并另外记下哪些成员实际参与了。

第二步：在轨迹里找实际行为

沿着运行标识，读取模型调用、工具操作、派发、消息和结果。对每个角色分别看三件事：它有没有收到任务？有没有开始执行？它的改动有没有被上级采纳？

通信看两类事件：

事件 含义
message_sent 消息已被接受并进入队列
message_refused 发送被拒绝，额外带 reason

两者的 payload 都有 from_aid、from_role、to_aid、to_role。分析通信时，成功送达的和被拒绝的尝试都要保留。再往下查：

  • 接收方会话里的消息和之后的模型调用，能说明它是否真的用上了这条消息。
  • 按 message_id 关联持久化的消息，可以区分同一对角色之间的多次交接。
  • commit_refs 保存消息携带的 Git 对象引用，用来核对候选代码是从谁传给谁的。

轨迹的读法见 运行记录。

常见问题对应的材料

想回答的问题 需要对照的材料
所有角色都参与了吗 声明名册、实际的模型与工具事件
谁向谁派发或发送 拓扑声明、操作尝试和成功回执
有没有角色越权干了别人的活 工具集合、提示词和实际执行
最终交付来自哪个候选 采纳记录、候选补丁与最终目录
几次运行的条件是否相同 模型、工具、预算与上下文配置

怎样算出依从性指标

先定义“一次运行算符合声明”的判定条件，再按这个条件统计比例。注意几点：

  • 论文结果和你新做的应用实验，各自对应自己的配置和轨迹，不能混用。
  • 想解释因果，或比较两种团队谁更好，还要结合任务质量、实验条件和研究说明。
  • 单成员参与率、全部声明成员参与率、通信边覆盖率，各自回答不同的问题。汇总时同时看指标的分母和缺失状态。

批量分析去哪里做

OC 负责保存通用的运行和协作记录；OCE（OpenCollab-Eval）负责实验配置、批量分析和报告。批量研究从 OCE 实验工具说明 进入，相关模块：

  • cell_report_rows：解释轨迹和角色参与。
  • cell_report_statistics：汇总选定的尝试、通信与角色统计，并计算相应区间。
  • cell_report_rendering：输出文字与 JSON。
  • batch_reporting：维护重试、替换和撤回的选择。
  • experiment/analysis：研究批次的原始分析脚本，按对应的批次版本和条件使用。

不用 OCE 也行：应用可以用公开的团队配置读取接口加事件记录，搭自己的观察视图。建议先拿少量运行核对事件和角色对不对，再汇总整批，这样能早点发现漏记、重复累计和角色对应错误。
