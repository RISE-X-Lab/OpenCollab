# 采用队友改动并验证交付

在 OC 的 Team 里，Coder 子成员通常在独立工作区（工作树或容器）改代码，它的改动不会自动写回团队的交付目录。`adopt_agent` 是入口成员显式"合入"的那一步：传入已完成 Coder 的 `aid`，运行时把它的增量补丁应用到交付目录。OC 的推荐流程是先采用，再派一个新的 Tester，让测试跑在真正交付的文件上，而不是 Coder 自己的副本上。最小用法是入口调用 `{"aid": 3}`。

## 怎么做

1. 确认入口角色的 `tools` 里有 `adopt_agent`。
2. 等 Coder 成功完成。完成结果里会带上可以采用的 aid（OC 给每个成员分配的整数编号），例如 `Completed coder aid=3`。
3. 入口发出工具调用，只需要一个参数：

   ```json
   {"aid": 3}
   ```

4. 采用成功后，派一个新的 Tester 检查交付目录：

   ```json
   {"role": "tester", "task": "验证刚采用的 parser 修复，执行相关回归测试并报告命令、退出码和失败信息。", "context": "检查当前交付目录中的空输入处理。"}
   ```

   新 Tester 会从已经更新的交付内容准备环境，所以测试结果对应的正是这次实际交付的内容。

5. 最终报告写清三件事：改了哪些文件、采用是否成功、执行了哪些项目验证。测试命令的退出码和测试目标是否真的执行，一起说明验证结果。完整回答可以关联本次运行的产物记录。

## 什么情况下能采用

`aid` 必须是正整数。运行时会检查下面几条，全部满足才会执行：

- 调用者是拥有 `adopt_agent` 的入口成员。
- 对象是它的直接 coder 子成员。角色名按规范化后的形式比对。
- 对象在当前这一轮入口任务里已经成功完成。

如果对象失败了、被停止了、是别的角色，或者是之前某一轮的结果，要先处理它的状态，才能走对应的交付流程。

## 改动是怎样合进去的

声明了采纳工具的 Team，会按下面的过程处理：

1. 派发子任务时，用当前的源文件准备子任务环境。这包括你还没提交的修改和之前已经采用的实现。
2. Coder 在自己的环境里修改。完成后，运行时记录下它的全部变化。
3. 采用时，把这份候选改动的增量合入交付目录，源仓库的索引（Git 暂存区）保持不变。

不同环境下，你看到改动的时间不同：

| 环境 | 什么时候能在交付目录看到改动 |
| --- | --- |
| 共享环境 | Coder 已经直接改了交付目录，工具会告诉你这些变化已经存在 |
| 独立环境 | 工具成功返回采用结果之后 |
| 入口自己也被显式隔离 | 还要取出入口补丁，见 [把候选结果采纳到交付目录](../isolation/candidate-delivery.md) |

## 修订后再次采用

在同一轮入口任务里，同一个 Coder 又完成了新一版修订时：

- 运行时会算出它相对于上次成功采用的增量，再次采用只应用新增的部分。
- 重复采用完全相同的完成结果，会返回 already adopted，交付文件保持不变。

## 常见问题

如果同一个文件发生冲突，采用会被拒绝，交付文件保持原样。错误信息会指出完整候选材料保存在哪里。处理方法：

1. 先导出补丁。
2. 比较源目录和候选之间的实际差异，再处理冲突。
3. 或者派一个新任务，让它从已更新的交付目录继续修改。

如果采用失败，完整候选补丁会保存在本次运行的产物里。没有启用产物目录时，会存进一个私有临时恢复目录。要在释放运行资源之前保存好这些材料，恢复步骤见 [找回隔离任务的改动并清理资源](../isolation/workspace-recovery.md)。
